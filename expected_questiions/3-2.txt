A user accidentally deletes several files from the file share. You need to restore only the deleted files to the original location. What should you select as the restore type?
Your answer is correct
File Recovery with Original Location as the recovery destination
Explanation
For snapshot-based backups, item-level restore is supported. To restore individual files to the original location, you select File Recovery and choose Original Location as the recovery destination. You can then select the specific files to restore and choose to skip or overwrite existing files. Reference: https://learn.microsoft.com/en-us/azure/backup/restore-afs
Full Share Recovery with Alternate Location as the destination
Explanation
Full Share Recovery restores the entire file share, not individual files. This option would restore all data, not just the deleted files. Additionally, restoring to an alternate location does not meet the requirement to restore to the original location. Reference: https://learn.microsoft.com/en-us/azure/backup/restore-afs
File Recovery with Alternate Location as the recovery destination
Explanation
While File Recovery does support restoring individual files, selecting Alternate Location would restore the files to a different location rather than the original location. The requirement specifies restoring files to the original location. Reference: https://learn.microsoft.com/en-us/azure/backup/restore-afs
Full Share Recovery with Original Location as the destination
Explanation
Full Share Recovery restores the complete file share contents, not individual files. While this could recover the deleted files, it would also restore all other data and potentially overwrite any changes made since the backup, which is not the targeted solution required. Reference: https://learn.microsoft.com/en-us/azure/backup/restore-afs

You plan to create a service endpoint policy to restrict access to specific Azure Storage accounts. Which limitation applies to service endpoint policies?

The key limitation of service endpoint policies is:

They can only be used to filter access to Azure Storage accounts that are in the same region as the virtual network.

Why this matters
Service endpoint policies are designed to restrict outbound traffic from a subnet (with Microsoft.Storage service endpoint enabled) to specific Azure Storage accounts, but they have a regional constraint.

Important limitation to remember:
❗ Only Azure Storage accounts in the same region as the VNet are supported

So in your scenario:
VNet1 + Subnet1 (with Microsoft.Storage service endpoint)

You can only apply the policy to Storage accounts located in the same Azure region as VNet1

That’s the exam-trap detail:
Service endpoints can work cross-region in some scenarios, but service endpoint policies cannot.

If you see options about:

only private endpoints ❌

The correct concept remains:
👉 regional restriction (same region only)


Service endpoint policies can only be applied to storage accounts in the same region.
Explanation
Service endpoint policies for Azure Storage have global scope. When service endpoint policies are applied, the Azure Storage service endpoint scope is upgraded from regional to global, meaning policies can target storage accounts in any region. Reference: https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-service-endpoint-policies-overview
Correct answer
Service endpoint policies do not apply to traffic from on-premises networks.
Explanation
Service endpoint policies only apply to traffic from subnets associated with the policies. Traffic from on-premises networks to Azure services must be filtered using network virtual appliances or firewalls since service endpoint policies cannot filter this traffic. Reference: https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-service-endpoint-policies-overview
Service endpoint policies require a minimum subnet size of /24.
Explanation
There is no minimum subnet size requirement for service endpoint policies. The policy can be applied to any subnet that has service endpoints configured regardless of the subnet's address space size. Reference: https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-service-endpoint-policies-overview
Service endpoint policies can only allow access to one storage account per policy.
Explanation
Service endpoint policies can allow access to multiple storage accounts. You can add multiple storage account resources to a single policy, and multiple policies can be associated with a subnet. When multiple policies are associated, traffic to resources specified across any of these policies is allowed. Reference: https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-service-endpoint-policies-overview

Create a security group containing the computer accounts and assign the Reader role to the group at the storage account level.
Explanation

You have an Azure subscription that contains a virtual network named VNet1 in the East US region. VNet1 contains three virtual machines: VM1, VM2, and VM3. You create an application security group named ASG-Web in the East US region and add VM1 and VM2 as members. You plan to create a network security group rule that allows inbound traffic on TCP port 443 from ASG-Web to ASG-DB. You need to identify which virtual machines can be members of ASG-DB. What should you identify?
Any virtual machine in the East US region
Explanation
The constraint is based on the virtual network, not the region. Although ASGs must be created in a specific region, network interfaces from different virtual networks in the same region cannot be in the same ASG, nor can they be used together as source and destination in the same NSG rule. Reference: https://learn.microsoft.com/en-us/azure/virtual-network/application-security-groups
Correct answer
Only virtual machines in VNet1
Explanation
All network interfaces assigned to an application security group must exist in the same virtual network as the first network interface assigned to the group. If you specify an ASG as the source and destination in a network security group rule, the network interfaces in both ASGs must exist in the same virtual network. Since ASG-Web contains network interfaces from VNet1, ASG-DB must also contain only network interfaces from VNet1 for the rule to be valid. Reference: https://learn.microsoft.com/en-us/azure/virtual-network/application-security-groups
Your answer is incorrect
Only VM3
Explanation
While VM3 is eligible to be a member of ASG-DB since it is in VNet1, it is not the only virtual machine that could be a member. Any virtual machine in VNet1 that is not already a member of ASG-Web can be a member of ASG-DB, as well as VM1 and VM2 which can belong to multiple ASGs. Reference: https://learn.microsoft.com/en-us/azure/virtual-network/application-security-groups
Any virtual machine in the Azure subscription
Explanation
Virtual machines from different virtual networks cannot be members of an ASG if that ASG will be used in an NSG rule where another ASG from a different virtual network is the source or destination. The virtual network constraint applies regardless of subscription boundaries. Reference: https://learn.microsoft.com/en-us/azure/virtual-network/application-security-groups

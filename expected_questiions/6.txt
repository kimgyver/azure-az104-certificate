**Logic App(로직 앱)**은 Azure에서 제공하는 서버리스 워크플로 자동화 서비스야.

쉽게 말하면:

👉 “여러 시스템을 연결해서 자동으로 작업을 수행해주는 자동화 봇” 같은 서비스

🔧 어떤 역할을 하나?

Logic App은 조건이 발생하면 정해진 작업을 자동으로 실행해.

예를 들어:

Azure Budget 초과 → 이메일 보내기
파일이 Blob Storage에 업로드됨 → 자동으로 처리/변환
HTTP 요청 들어옴 → 다른 API 호출
DB에 데이터 들어옴 → Slack 알림 보내기
🧠 쉽게 이해하면
IF this happens (트리거)
THEN do this (액션들)

예:

Budget 초과 발생
   ↓
Logic App 실행
   ↓
Slack 알림 + 이메일 전송 + 티켓 생성
⚙️ 구성 요소
Trigger (트리거)
시작 조건
예: HTTP 호출, 스케줄, Budget 초과 등
Actions (액션)
수행할 작업들
이메일 보내기, API 호출, DB 업데이트 등
Connectors (커넥터)
Azure, Office 365, GitHub, Salesforce 같은 외부 서비스 연결
💡 Azure Budget과 연결되는 이유

Budget이 초과되면:

Logic App이 자동 실행되고
이메일/Teams/Slack 알림 보내거나
자동으로 Azure Function 실행 가능
🆚 비슷한 개념
AWS → Step Functions / EventBridge
Azure → Logic Apps
간단한 버전 → Power Automate (비즈니스용 UI 기반)

정답은:

✅ Azure NAT Gateway
🧠 이유

Azure Container Instances (ACI)가 Virtual Network(VNet) 안에 배포된 경우, 기본적으로 outbound 인터넷 트래픽은 다음 방식으로 처리됩니다:

VNet 내부에서는 공인 IP가 없으면 인터넷으로 나갈 수 없음
ACI는 기본적으로 “managed outbound” 또는 “user-defined NAT”가 필요
🚀 해결 방법
👉 VNet에 NAT Gateway를 연결
Subnet에 NAT Gateway를 붙이면
해당 subnet의 모든 outbound 트래픽이 NAT를 통해 인터넷으로 나감
🔧 구조
ACI Container Group
        ↓
Subnet (VNet)
        ↓
NAT Gateway
        ↓
Internet
❌ 다른 선택지들이 아닌 이유
❌ Public IP directly on ACI
VNet 배포된 ACI에서는 제한적
안정적인 outbound 해결책 아님
❌ Load Balancer
outbound 인터넷 트래픽 해결용이 아님
❌ Application Gateway
HTTP routing 용도 (outbound 아님)
💡 핵심 포인트 (시험용)

👉 VNet 안의 PaaS/compute가 outbound 인터넷 필요하면

정답 거의 항상: NAT Gateway
🎯 한 줄 암기

VNet 내부 리소스의 outbound internet = NAT Gateway

👉 Network Address Translation (네트워크 주소 변환)

🧠 의미 쉽게 설명

NAT는 한마디로:

👉 “사설 IP를 공인 IP로 바꿔서 인터넷 통신이 가능하게 해주는 기술”

🔧 왜 필요할까?
내부 네트워크 (Private IP)

예:

👉 이런 IP들은 인터넷에서 직접 접근 불가능

인터넷 나갈 때

🌍 NAT가 하는 일

2. Return traffic 매핑

👉 “여러 private 리소스가 하나의 public IP로 인터넷 나가게 해주는 관리형 서비스”

이거 같은 말이지? Full share recovery to an alternate location only
Explanation
Vaulted backup for Azure Files currently supports only full share recovery to an alternate location. Original location restores (OLR) and file-level recovery are not supported from vault-tier recovery points. You can perform restore to an empty folder with the Overwrite option only. This ensures data isolation during recovery from security incidents. Reference: https://learn.microsoft.com/en-us/azure/backup/azure-file-share-support-matrix

⚡ Kubernetes vs Azure Container Instances (ACI) 리소스 처리 차이
🧠 핵심 한 줄

Kubernetes는 “request + limit 모델”, ACI는 “request = limit처럼 동작”

🔧 1. Kubernetes (K8s)
📦 리소스 개념 2개 존재
✔ Request
스케줄링 기준 (보장 최소값)
노드에 배치할 때 사용
✔ Limit
실제 사용 가능한 최대치 (hard cap)
💡 동작 방식
resources:
  requests:
    cpu: "1"
    memory: "1Gi"
  limits:
    cpu: "2"
    memory: "2Gi"
👉 의미
최소 1 CPU 보장
최대 2 CPU까지 사용 가능
초과하면 throttling 또는 OOM kill
🚨 특징
request < limit 가능
limit 초과 시 강제 제한
Pod 간 자원 공유 + 경쟁 존재
☁️ 2. Azure Container Instances (ACI)
📦 리소스 개념
request만 설정
limit은 없음 (또는 자동 request = limit)
💡 동작 방식
CPU request = MAX CPU
Memory request = MAX Memory
🚨 특징
container 간 “노드 경쟁 없음”
각 container가 독립적으로 quota 가짐
request가 사실상 upper bound
⚔️ 핵심 비교
항목	Kubernetes	ACI
리소스 모델	request + limit	request only
max control	limit	request
초과 사용	throttling / kill	불가능
스케줄링 기준	request	없음 (managed)
리소스 공유	있음	제한적/격리
🔥 중요한 시험 포인트
❗ Kubernetes

request = 보장, limit = 최대

❗ ACI

request = 최대 사용량

💡 쉽게 외우는 법
Kubernetes = “범위 있음 (min ~ max)”
ACI = “딱 정해진 박스”
🎯 한 줄 정리

Kubernetes는 request/limit 둘 다 있는 세밀한 제어 모델이고, ACI는 request가 사실상 최대 리소스 제한 역할을 한다.

NIC

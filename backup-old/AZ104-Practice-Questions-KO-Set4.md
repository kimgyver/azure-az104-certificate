## 1) 네트워킹

### 문제 1
포트 80에서 웹 애플리케이션을 실행하는 Azure 가상 머신이 있습니다. 사용자들이 웹 애플리케이션에는 접근할 수 있지만 응답을 받지 못한다고 보고합니다. NSG 인바운드 규칙에서 포트 80 트래픽이 허용된 것을 확인했습니다. 응답 트래픽을 허용하기 위해 아웃바운드 규칙을 만들어야 하는지 결론을 내려야 합니다. 무엇을 결론으로 도출해야 합니까?

- A. 포트 80에 아웃바운드 NSG 규칙을 만들어 반환 트래픽을 허용해야 한다
- B. NSG는 Stateful이므로 아웃바운드 규칙이 필요 없다
- C. 암호화된 응답을 허용하기 위해 포트 443에 아웃바운드 NSG 규칙을 만들어야 한다
- D. 가상 네트워크를 통해 반환 트래픽을 허용하는 UDR을 구성해야 한다

**정답: B**
**설명:**
Azure 네트워크 보안 그룹은 **Stateful**입니다. 인바운드 트래픽이 포트에서 허용되면, 해당 연결의 아웃바운드 반환 트래픽은 자동으로 허용됩니다. NSG는 흐름 레코드를 통해 연결 상태를 추적하므로 수립된 연결에 대해 별도의 아웃바운드 규칙 없이 통신이 허용됩니다.

사용자가 애플리케이션에 접근하지만 응답이 없는 경우 가능한 원인:
- 애플리케이션 레벨 버그 또는 잘못된 설정 (웹 서버가 응답을 보내지 않음)
- OS 레벨 방화벽 (iptables, Windows 방화벽)
- 로드 밸런서 상태 프로브 실패
- NIC 레벨 네트워크 문제

**핵심 규칙**: 이미 허용된 인바운드 포트에 대한 응답 트래픽에는 NSG 아웃바운드 규칙이 필요하지 않습니다.

### 문제 2
NVA(네트워크 가상 어플라이언스)에 대한 고가용성을 제공하기 위해 내부 Azure Standard Load Balancer를 배포하려고 합니다. 로드 밸런서는 모든 포트의 모든 TCP 및 UDP 트래픽을 NVA로 부하 분산해야 합니다. 적절한 부하 분산 규칙을 구성해야 합니다. Protocol 및 Port 설정에 어떤 값을 사용해야 합니까?

- A. Protocol: TCP, Port: 443
- B. Protocol: UDP, Port: 0
- C. Protocol: All, Port: 0
- D. Protocol: TCP, Port: Any

**정답: C**
**설명:**
NVA(방화벽, IDS/IPS, 프록시)의 경우 포트 레벨 필터링 없이 모든 트래픽을 전달해야 합니다. Azure Standard Load Balancer에서 **HA Ports 규칙**이 필요합니다:

| 설정 | 값 | 이유 |
|------|----|----|
| Protocol | All | TCP와 UDP 모두 처리 |
| Port | 0 | 모든 포트를 나타내는 와일드카드 |

이 조합은 **HA Ports 규칙**을 생성하며, NVA 시나리오에서 프로토콜이나 포트에 관계없이 모든 패킷이 어플라이언스에 의해 검사되어야 하는 경우에 사용됩니다.

**일반 웹 LB 규칙과 비교**: Protocol TCP, Port 80/443 — 특정 웹 트래픽만 처리합니다.

### 문제 3
Azure CLI를 사용하여 ARM 템플릿으로 Azure 가상 머신을 배포하고 있습니다. 배포에 `az deployment group create` 명령을 사용합니다. 유효성 검사 중에 리소스가 생성되지 않도록 배포 전에 템플릿 구문을 검증해야 합니다. 어떤 명령을 실행해야 합니까?

- A. `az deployment group create --what-if`
- B. `az deployment group validate`
- C. `az deployment group preview`
- D. `az template validate`

**정답: B**
**설명:**
| 명령 | 목적 | 리소스 생성 여부 |
|------|------|----------------|
| `az deployment group create` | 실제 배포 | 예 |
| `az deployment group validate` | 구문 + 스키마 + 매개변수 유효성 검사 | **아니요** |
| `az deployment group what-if` | 리소스 변경 미리 보기 | 아니요 |

**`az deployment group validate`** 검사 내용:
- JSON 구문 정확성
- 필수 매개변수 존재 여부
- ARM 템플릿 스키마 준수
- 기본 배포 유효성 검사

리소스를 배포하지 않습니다. `create` 전에 사전 검사로 사용합니다.

**`what-if`**도 변경을 적용하지 않지만 더 나아가 생성, 수정 또는 삭제될 리소스를 정확히 보여줍니다.

### 문제 4
Azure 가상 머신에 대한 메트릭 경고 규칙을 생성하고 있습니다. 경고 규칙에 두 가지 조건을 추가합니다: CPU 사용률 90% 초과 AND 사용 가능한 메모리 바이트 1GB 미만. 경고는 언제 발생합니까?

- A. 평가 기간 내에 어느 시점에서든 둘 중 하나의 조건이 충족되었을 때
- B. 서로 다른 시점이라도 평가 기간 내에 두 조건이 모두 충족된 경우
- C. 동일한 평가 기간 동안 두 조건이 동시에 충족될 때
- D. 두 조건의 평균이 각각의 임계값을 초과할 때

**정답: C**
**설명:**
**AND** 로직이 있는 Azure 메트릭 경고는 창 내의 서로 다른 시점에서 각각 true일 때가 아니라, 동일한 평가 데이터 포인트에서 **모든 조건이 동시에 true**일 때만 발생합니다.

**예시:**
| 시간 | CPU > 90%? | 메모리 < 1GB? | 경고 발생? |
|------|-----------|--------------|----------|
| 10:01 | ✅ 예 | ❌ 아니요 | ❌ 아니요 |
| 10:04 | ❌ 아니요 | ✅ 예 | ❌ 아니요 |
| 10:07 | ✅ 예 | ✅ 예 | ✅ 예 |

**"기간 내 어느 시점이든 true" 동작 구현 방법**: CPU에는 **Max**(예: 5분 동안 Max CPU > 90%), 메모리에는 **Min**(5분 동안 Min 메모리 < 1GB) 등의 집계를 사용합니다. 이렇게 하면 창 내 임계값이 한 번이라도 위반되면 집계 값이 이를 반영합니다.

### 문제 5
Azure 스토리지 계정에 스토리지 방화벽을 구성하여 액세스를 제한했습니다. 온-프레미스 서버의 공용 IP 주소를 IP 네트워크 규칙에 추가했습니다. East US 지역의 Azure 가상 머신 사용자들이 가상 네트워크가 같은 지역에 있음에도 불구하고 스토리지 계정에 액세스할 수 없다고 보고합니다. 가상 머신이 스토리지 계정에 액세스하도록 설정해야 합니다. 무엇을 해야 합니까?

- A. VM의 공용 IP 주소를 스토리지 계정 IP 네트워크 규칙에 추가한다
- B. 스토리지 계정의 공용 액세스를 활성화한다
- C. VM의 서브넷에서 Microsoft.Storage에 대한 서비스 엔드포인트를 활성화하고 스토리지 계정에 가상 네트워크 규칙을 추가한다
- D. 스토리지 계정과 가상 네트워크 간에 피어링 연결을 만든다

**정답: C**
**설명:**
Azure VM은 예측 가능한 공용 IP가 아닌 Azure 내부 네트워크를 통해 스토리지와 통신합니다. IP 네트워크 규칙 추가는 VM 트래픽을 안정적으로 커버하지 못합니다.

올바른 접근 방식:
1. VM의 서브넷에서 **서비스 엔드포인트**(`Microsoft.Storage`) 활성화 — 트래픽이 공용 인터넷 대신 Azure 백본을 통해 라우팅됨
2. 특정 서브넷을 허용하는 **VNet 규칙**을 스토리지 계정에 추가

| 규칙 유형 | 제어 대상 | Azure VM에 적합? |
|----------|---------|----------------|
| IP 네트워크 규칙 | 공용 IP 주소 | ❌ (VM에는 고정 공용 IP 없음) |
| VNet 규칙 | 서브넷 ID | ✅ |

**핵심**: 스토리지 방화벽은 IP가 아닌 서브넷 ID를 기반으로 VNet 규칙을 평가하므로, 서비스 엔드포인트가 활성화되면 허용된 서브넷 내의 VM에 자동으로 액세스가 부여됩니다.

### 문제 6
Bicep 파일을 개발하여 스토리지 계정을 배포하고 있습니다. `deployStorage`라는 매개변수가 `true`로 설정된 경우에만 스토리지 계정을 조건부로 배포해야 합니다. 리소스 선언에 어떤 구문을 사용해야 합니까?

- A. `resource storageAccount '...' = condition (deployStorage) { ... }`
- B. `resource storageAccount '...' = if (deployStorage) { ... }`
- C. `resource storageAccount '...' [if deployStorage] { ... }`
- D. `resource storageAccount '...' = when (deployStorage) { ... }`

**정답: B**
**설명:**
Bicep은 `= if (조건)`을 사용하여 리소스를 조건부로 선언합니다:

```bicep
param deployStorage bool

resource storageAccount 'Microsoft.Storage/storageAccounts@2023-01-01' = if (deployStorage) {
  name: 'mystorageaccount'
  location: resourceGroup().location
  sku: { name: 'Standard_LRS' }
  kind: 'StorageV2'
}
```

**Bicep vs ARM JSON 조건부 구문 비교:**

| | ARM JSON | Bicep |
|-|----------|-------|
| 구문 | `"condition": "[parameters('deployStorage')]"` | `= if (deployStorage)` |
| 스타일 | 리소스 블록 내부의 JSON 속성 | `=` 뒤에 인라인 |
| 가독성 | 장황함 | 간결함 |

`deployStorage`가 `false`이면 리소스 블록이 완전히 건너뜁니다 — 오류 없음, 배포 없음.

### 문제 7
여러 백엔드 서버가 있는 백엔드 풀을 가진 Azure Application Gateway가 있습니다. 동일한 사용자 세션의 후속 요청이 동일한 백엔드 서버로 전달되도록 해야 합니다. 솔루션은 Application Gateway 기능을 사용해야 합니다. 무엇을 구성해야 합니까?

- A. 부하 분산 규칙에서 소스 IP 선호도
- B. HTTP 설정에서 쿠키 기반 세션 선호도
- C. URL 경로 기반 라우팅 규칙
- D. 호스트 기반 라우팅 규칙

**정답: B**
**설명:**
**쿠키 기반 세션 선호도**(고정 세션이라고도 함)는 동일한 클라이언트의 요청이 항상 동일한 백엔드 서버로 라우팅되도록 합니다. Application Gateway는 첫 번째 응답에 쿠키(`ARRAffinity`)를 설정하고, 후속 요청에 이 쿠키가 포함되어 게이트웨이가 동일한 백엔드로 식별하고 라우팅할 수 있습니다.

**소스 IP 선호도를 사용하지 않는 이유?**
- 소스 IP 선호도는 Azure Load Balancer(L4) 개념
- Application Gateway는 L7에서 작동하며 고정성을 위해 쿠키 사용
- 소스 IP는 변경될 수 있음 (NAT, 프록시, 모바일 네트워크)

| 기능 | 레이어 | 고정성 메커니즘 |
|------|-------|--------------|
| Application Gateway | L7 | 쿠키 (ARRAffinity) |
| Azure Load Balancer | L4 | 소스 IP 해시 |

### 문제 8
Azure Firewall 정책에 애플리케이션 규칙이 구성되어 있습니다. Windows Update와 같은 Azure 서비스의 특정 FQDN(정규화된 도메인 이름)에 대한 아웃바운드 HTTP/S 트래픽을 허용해야 합니다. 규칙 구성을 단순화하고 Microsoft가 필요한 엔드포인트를 변경할 때 규칙이 자동으로 업데이트되도록 해야 합니다. 애플리케이션 규칙에서 무엇을 사용해야 합니까?

- A. 서비스 태그
- B. 수동으로 유지 관리되는 FQDN 목록
- C. FQDN 태그
- D. IP 그룹

**정답: C**
**설명:**
**FQDN 태그**는 잘 알려진 Azure 서비스와 관련된 FQDN 컬렉션을 Microsoft가 관리합니다. 애플리케이션 규칙에서 FQDN 태그를 사용하면 Azure Firewall이 기본 엔드포인트 목록을 자동으로 최신 상태로 유지합니다 — 수동 업데이트 불필요.

| 옵션 | 포함 내용 | 자동 업데이트? | 사용처 |
|------|----------|--------------|-------|
| FQDN 태그 | 사전 정의된 FQDN 그룹 (예: `WindowsUpdate`) | ✅ 예 | 애플리케이션 규칙 |
| 서비스 태그 | IP 주소 범위 | ✅ 예 | NSG / 네트워크 규칙 |
| IP 그룹 | 사용자 지정 IP 주소 컬렉션 | ❌ 아니요 | 네트워크 규칙 |

**시험 키워드**: "Microsoft가 엔드포인트를 변경할 때 자동으로 업데이트" → **FQDN 태그**

사용 가능한 FQDN 태그: `WindowsUpdate`, `AzureCloud`, `MicrosoftIntune`, `AzureKubernetesService` 등.

### 문제 9
클라우드 계층화를 포함한 Azure File Sync 배포를 계획하고 있습니다. 30일 내에 액세스되지 않은 파일은 Azure Files로 계층화하고 로컬 볼륨에서 최소 25% 여유 공간을 유지하도록 클라우드 계층화 정책을 구성해야 합니다. 어떤 두 가지 정책을 구성해야 합니까? (두 가지 선택)

- A. 캐시 크기 정책을 75%로 설정
- B. 날짜 정책을 30일로 설정
- C. 볼륨 여유 공간 정책을 25%로 설정
- D. 계층화 임계값 정책을 30일 유휴로 설정
- E. 대역폭 제한 정책

**정답: B, C**
**설명:**
Azure File Sync 클라우드 계층화에는 두 가지 독립적인 정책이 있습니다:

| 정책 | 제어 대상 | 설정 |
|------|---------|------|
| **날짜 정책** | 시간 기반 계층화: N일 내에 액세스되지 않은 파일은 계층화 대상이 됨 | 30일 |
| **볼륨 여유 공간 정책** | 오래된 파일을 적극적으로 계층화하여 로컬 볼륨에서 최소 여유 공간 비율 유지 | 25% |

이 두 정책은 **독립적으로** 작동합니다:
- **날짜 정책**은 파일이 계층화 대상이 되는 *시점*을 정의
- **볼륨 여유 공간 정책**은 사용 가능한 디스크 공간에 따라 계층화가 *얼마나 적극적으로* 이루어지는지 정의

두 요구사항을 충족하려면 두 정책이 모두 필요합니다.

**일반적인 함정**: 두 정책은 상호 배타적이지 않으며 동시에 활성화할 수 있고 그렇게 해야 합니다.

### 문제 10
ARM 템플릿을 사용하여 Azure 가상 머신을 배포하고 있습니다. 템플릿에는 배포 후 VM을 구성하는 사용자 지정 스크립트 확장이 포함되어 있습니다. VM은 제한적인 아웃바운드 규칙이 있는 NSG가 있는 가상 네트워크에 배포됩니다. 사용자 지정 스크립트 확장 실행이 실패합니다. VM 에이전트가 설치되어 실행 중임을 확인했습니다. 확장이 올바르게 작동하려면 VM에서 어떤 IP 주소에 액세스할 수 있어야 합니까?

- A. 10.0.0.1
- B. 169.254.169.254
- C. 168.63.129.16
- D. 100.64.0.0

**정답: C**
**설명:**
`168.63.129.16`은 플랫폼 레벨 통신에 사용되는 Azure의 **특수 가상 공용 IP**입니다:

| 목적 | 세부 사항 |
|------|---------|
| VM 에이전트 통신 | 확장이 Azure 플랫폼으로부터 명령 수신 |
| 확장 다운로드 및 실행 | 스크립트/패키지가 이 IP를 통해 가져와짐 |

| 상태 프로브 | Azure Load Balancer 상태 확인 |

**해결 방법**: 포트 80/443에서 `168.63.129.16`으로의 트래픽을 허용하는 아웃바운드 NSG 규칙을 추가하거나 `AzurePlatformDNS` / `AzurePlatformIMDS` 서비스 태그를 사용합니다.

**참고**: `169.254.169.254`는 IMDS(인스턴스 메타데이터 서비스) 엔드포인트 — 메타데이터 및 관리 ID 토큰에 사용되지만 확장에는 사용되지 않습니다.

- B. Incremental만 가능
- C. Complete와 Incremental 모두 가능
- D. 연결된 템플릿에는 배포 모드가 필요하지 않음

**배포 구조:**
```
메인 템플릿 (Incremental) → VM 배포
  └── 연결된 템플릿 (Incremental만) → NIC 배포
```

- A. 등록된 하나의 방법을 사용하여 암호 재설정이 성공한다
- B. User1에게 재설정 전에 추가 방법을 등록하라는 메시지가 표시된다

**설명:**
Azure Backup은 세 가지 스냅샷 일관성 유형을 지원합니다:

| 유형 | 캡처 내용 | 앱/DB 안전? | 속도 |
|------|---------|-----------|------|
| **크래시 일관성** | 디스크 상태만 (메모리/트랜잭션 없음) | ❌ | 가장 빠름 |
| 파일 일관성 | 디스크 + OS 파일 시스템 플러시 | 부분적 | 중간 |
| **애플리케이션 일관성** | 디스크 + OS + VSS를 통한 앱 중지 | ✅ | 가장 느림 |

**크래시 일관성**은 갑작스러운 전원 차단 후 상태와 유사합니다:
- 디스크 데이터가 있는 그대로 캡처됨
- 메모리 내 데이터 및 진행 중인 트랜잭션은 **포함되지 않음**
- 데이터베이스는 복원 시 복구가 필요할 수 있음 (트랜잭션 로그 재생)
- 가장 빠르고 오버헤드가 가장 낮음

**애플리케이션 일관성**은 VSS(Windows 볼륨 섀도 복사본 서비스) 또는 사전/사후 스크립트(Linux)를 사용하여 애플리케이션 쓰기를 일시 중지하고, 트랜잭션을 디스크로 플러시한 다음 스냅샷을 찍어 데이터베이스의 깨끗한 복구 지점을 제공합니다.

### 문제 19
Azure 스토리지 계정에 아카이브 티어에 Blob이 있습니다. 긴급한 비즈니스 요구 사항으로 인해 여러 Blob을 리하이드레이션해야 합니다. Blob의 크기는 10GB 미만이며 가능한 한 빨리 사용할 수 있어야 합니다. 어떤 리하이드레이션 우선 순위를 선택해야 합니까?

- A. 표준 우선 순위
- B. 높은 우선 순위
- C. 즉시 우선 순위
- D. 고속 우선 순위

**정답: B**
**설명:**
Azure Blob Storage 아카이브 티어 리하이드레이션 옵션:

| 우선 순위 | 일반적인 소요 시간 | 비용 | 사용 시기 |
|----------|----------------|------|---------|
| **표준** | 최대 15시간 이상 | 낮음 | 긴급하지 않은 복원 |
| **높음** | 10GB 미만 Blob의 경우 1시간 미만 | 높음 | 긴급 복원 ✅ |

**높은 우선 순위** 리하이드레이션은 표준 큐보다 먼저 요청을 처리합니다. 10GB 미만의 Blob의 경우 높은 우선 순위는 일반적으로 **1시간 미만**에 완료됩니다.

문제 조건 분석:
- "긴급한 비즈니스 요구 사항" → 높은 우선 순위
- "가능한 한 빨리" → 높은 우선 순위
- "10GB 미만" → 빠른 높은 우선 순위 완료 자격

**처리 방법**: 아카이브에서 핫 또는 쿨(동시에 둘 다는 불가)로 티어를 설정하고 우선 순위를 지정합니다:
```
az storage blob set-tier --account-name ... --container-name ... --name blob.dat \
  --tier Hot --rehydrate-priority High
```

### 문제 20
Azure 구독에 여러 스토리지 계정이 있습니다. 스토리지 계정의 리소스 로그를 Log Analytics 작업 영역으로 전송하도록 진단 설정을 구성해야 합니다. 로그 수집을 단순화하기 위해 범주 그룹을 사용하려고 합니다. 진단 설정을 구성할 때 사용할 수 있는 두 가지 범주 그룹은 무엇입니까? (두 가지 선택)

- A. metrics
- B. allLogs
- C. audit
- D. diagnosticLogs
- E. operationalLogs

**정답: B, C**
**설명:**
Azure 진단 설정은 각 범주를 개별적으로 선택하지 않고 사전 정의된 로그 범주 세트를 수집하는 간소화된 방법으로 **범주 그룹**을 제공합니다.

대부분의 Azure 리소스(스토리지 계정 포함)에서 사용할 수 있는 두 가지 표준 범주 그룹은 다음과 같습니다:

| 범주 그룹 | 포함 내용 |
|---------|---------|
| **allLogs** | 해당 리소스 유형에 대해 지원되는 모든 리소스 로그 범주 |
| **audit** | 보안 및 액세스 관련 로그 범주 (인증, 권한 부여, 액세스 이벤트) |

**나머지가 틀린 이유:**
- `metrics` — 메트릭은 별도의 차원 (로그 범주 그룹이 아님)
- `diagnosticLogs` — Azure에서 인식되는 범주 그룹 이름이 아님
- `operationalLogs` — 표준 Azure 범주 그룹 이름이 아님

**사용 예시** (Azure Portal): 진단 설정 추가 시 "로그" 아래에서 개별 범주 또는 범주 그룹(allLogs, audit)의 체크박스가 표시됩니다. `allLogs`를 선택하면 해당 리소스의 현재 및 미래의 모든 로그 범주가 자동으로 포함됩니다.

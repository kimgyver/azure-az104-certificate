### 문제 1

회사에 여러 부서가 있고 각 부서에는 여러 가상 머신(VM)이 있습니다. 모든 VM은 동일한 리소스 그룹 RG1에 있습니다. 청구 및 관리 목적으로 각 VM을 해당 부서와 연결하려고 합니다.

**어떻게 해야 합니까?**

- A. 각 부서에 대한 Azure 관리 그룹 생성
- B. 각 부서에 대한 별도의 리소스 그룹 생성
- C. 가상 머신에 태그 할당
- D. 가상 머신 설정 수정

**✅ 정답: C**

**해설:**
태그(Tags)는 리소스에 연결하는 이름-값 쌍으로, 조직화, 청구, 관리에 활용됩니다. 리소스 그룹 구조를 변경하지 않고 리소스를 특정 부서와 연결하는 올바른 도구입니다. 관리 그룹은 구독을 구성하는 도구이지 개별 리소스를 위한 것이 아닙니다. VM을 별도의 리소스 그룹으로 이동하는 것은 작업이 많고 단순 분류에는 적합하지 않습니다.

### 문제 2

글로벌 관리자 그룹 구성원이 신뢰할 수 없는 위치에서 연결할 때 Multi-Factor Authentication과 Azure AD 조인 장치를 사용하도록 요구하는 조건부 액세스 정책을 구현하려고 합니다.

**해결 방법: Multi-Factor Authentication 페이지에 액세스하여 사용자 설정을 변경합니다. 이 해결 방법이 요구 사항을 충족합니까?**

- A. 예
- B. 아니요

**✅ 정답: B**

**해설:**
사용자별 MFA 설정 페이지는 위치 기반 조건이나 장치 준수 요구 사항 같은 조건부 액세스 로직을 지원하지 않습니다. 신뢰할 수 없는 위치에서만 MFA를 요구하고 Azure AD 조인 장치를 강제하려면, "MFA 필요"와 "Azure AD 조인 장치 필요" 부여 제어(Grant Control)를 사용하는 **조건부 액세스 정책**을 설정해야 합니다.

### 문제 3

글로벌 관리자가 신뢰할 수 없는 위치에서 MFA 및 Azure AD 조인 장치를 사용하도록 조건부 액세스 정책을 설정하려고 합니다.

**해결 방법: Azure 포털에서 Azure AD 조건부 액세스 정책의 부여 제어(Grant Control)를 수정합니다. 이 해결 방법이 요구 사항을 충족합니까?**

- A. 예
- B. 아니요

**✅ 정답: A**

**해설:**
조건부 액세스 정책의 **부여 제어(Grant Control)**는 액세스가 허용되기 전에 충족해야 할 조건을 지정하는 곳입니다. 여기서 "Multi-Factor Authentication 필요"와 "장치가 규격 준수로 표시되어야 함" 또는 "하이브리드 Azure AD 조인 장치 필요"를 설정할 수 있습니다. MFA와 장치 요구 사항을 모두 동시에 구성하는 올바른 위치입니다.

### 문제 4

회사의 Azure AD 테넌트가 온프레미스 Active Directory와 하이브리드 공존으로 구성되어 있습니다. DirSync 서버(Azure AD Connect)가 실행 중입니다. 온프레미스 AD에 새 사용자를 생성했고 즉시 Azure AD에 복제해야 합니다.

**해결 방법: `Start-ADSyncSyncCycle -PolicyType Delta`를 실행합니다. 이 해결 방법이 목표를 충족합니까?**

- A. 예
- B. 아니요

**✅ 정답: A**

**해설:**
`Start-ADSyncSyncCycle -PolicyType Delta`는 Azure AD Connect에서 즉각적인 델타 동기화 사이클을 트리거합니다. 이는 마지막 동기화 이후의 변경 사항(새 사용자 포함)을 온프레미스 AD에서 Azure AD로 전송합니다. 델타 동기화는 모든 개체를 처리하지 않고 변경 사항만 처리하므로 초기(`-PolicyType Initial`) 동기화보다 빠릅니다.

### 문제 5

리소스 그룹에 여러 리소스가 있습니다. 실수로 리소스가 삭제되는 것을 방지하고 싶지만, 사용자들은 여전히 리소스 구성을 수정할 수 있어야 합니다.

**어떤 리소스 잠금을 적용해야 합니까?**

- A. 각 리소스에 ReadOnly 잠금
- B. 리소스 그룹에 Delete 잠금
- C. 리소스 그룹에 ReadOnly 잠금
- D. 각 리소스에 개별적으로 Delete 잠금

**✅ 정답: B**

**해설:**
리소스 그룹에 적용된 **Delete 잠금**은 리소스 그룹 및 그 안의 모든 리소스(잠금이 상위에서 하위로 상속됨)의 삭제를 방지하면서 구성 수정은 허용합니다. ReadOnly 잠금은 삭제와 수정을 모두 방지하므로 너무 제한적입니다. 각 리소스에 개별적으로 잠금을 적용하는 것은 상위 리소스 그룹의 잠금이 상속되므로 불필요합니다.

### 문제 6

Azure 구독의 모든 리소스에 "CostCenter" 태그가 있는지 확인해야 합니다. 일부 리소스에는 이 태그가 없습니다.

**어떻게 해야 합니까?**

- A. 각 리소스에 리소스 잠금 적용
- B. "리소스에 태그 필요" 정의로 Azure 정책을 만들고 구독에 할당
- C. 미준수 리소스에 수동으로 태그 추가
- D. 관리 그룹을 만들고 여기에 태그 적용

**✅ 정답: B**

**해설:**
핵심은 **정책 정의(Definition)를 만드는 것**이 아니라 **구독 범위에 정책 할당(Assignment)**까지 해야 효과가 생긴다는 점입니다.

- 포털 경로: `Policy` → `Definitions`(기본 제공 `Require a tag on resources`) 확인 → `Assignments` → Scope를 구독으로 지정
- 효과(Effect): `Audit`(미준수 감시) 또는 `Deny`(생성/수정 차단)
- 시험 포인트: "태그를 강제"는 거의 항상 RBAC/잠금이 아니라 Azure Policy로 해결

관리 그룹은 태그를 직접 붙이는 기능이 아니고, 수동 태깅은 미래 생성 리소스까지 자동 강제하지 못합니다.

### 문제 7

조직에 여러 Azure 구독이 있습니다. 모든 구독에 걸쳐 대규모로 액세스와 정책을 관리해야 합니다.

**어떤 Azure 기능을 사용해야 합니까?**

- A. 리소스 그룹
- B. Azure 정책(Policy)
- C. 관리 그룹(Management Groups)
- D. Azure Blueprints

**✅ 정답: C**

**해설:**
**관리 그룹**은 여러 구독을 구성하는 컨테이너입니다. 관리 그룹 수준에서 적용된 정책, RBAC 역할 할당, 이니셔티브는 해당 관리 그룹 내의 모든 구독에 상속됩니다. 관리 그룹은 루트를 제외하고 최대 6단계 깊이까지 중첩될 수 있습니다.

### 문제 8

귀하는 구독 수준에서 **기여자(Contributor)** 역할을 받았습니다. 동료가 특정 리소스 그룹에서 귀하에게 **소유자(Owner)** 역할을 할당하려 합니다.

**동료가 기여자 역할만 가지고 있다면 소유자 역할을 할당할 수 있습니까?**

- A. 예, 기여자는 리소스에 대한 전체 액세스 권한이 있으므로
- B. 아니요, 기여자는 역할을 할당할 수 없음 — 사용자 액세스 관리자 또는 소유자 역할이 필요함
- C. 예, 역할 할당은 구독에서 상속되므로
- D. 아니요, 소유자 역할은 리소스 그룹 수준에서 할당할 수 없으므로

**✅ 정답: B**

**해설:**
**기여자** 역할은 Azure 리소스에 대한 전체 읽기/쓰기 액세스를 부여하지만 명시적으로 **액세스 관리(역할 할당)를 할 수 없습니다**. 역할을 할당하려면 **소유자** 또는 **사용자 액세스 관리자** 역할이 필요합니다. 이것이 Azure RBAC의 핵심 구분점입니다.

### 문제 9

사용자가 VM을 시작, 중지, 크기 조정하는 등 가상 머신을 관리할 수 있어야 합니다. 가상 네트워크나 스토리지 계정에 대한 액세스는 없어야 합니다.

**어떤 기본 제공 역할을 할당해야 합니까?**

- A. 기여자(Contributor)
- B. 소유자(Owner)
- C. 가상 머신 기여자(Virtual Machine Contributor)
- D. 읽기 권한자(Reader)

**✅ 정답: C**

**해설:**
**가상 머신 기여자** 기본 제공 역할은 VM 관리(생성, 시작, 중지, 크기 조정, 삭제) 권한을 부여하지만 VM이 사용할 수 있는 가상 네트워크나 스토리지 계정에 대한 액세스는 부여하지 않습니다. 기여자 역할은 범위 내 모든 리소스에 너무 광범위한 액세스를 부여합니다.

### 문제 10

조직의 SSPR(셀프 서비스 암호 재설정)을 구성 중입니다. 사용자들이 Azure AD 암호를 재설정했지만 온프레미스 Active Directory 암호는 변경되지 않아 문제가 발생하고 있습니다.

**이 문제를 해결하기 위해 무엇이 필요합니까?**

- A. Azure AD Connect 델타 동기화 구성
- B. SSPR에서 비밀번호 쓰기 저장(Password Writeback) 활성화 - Azure AD Premium P1 또는 P2 필요
- C. 비밀번호 쓰기 저장 활성화 - Azure AD 무료 요금제에서도 사용 가능
- D. 모든 도메인 컨트롤러에 추가 Azure AD Connect 에이전트 설치

**✅ 정답: B**

**해설:**
**비밀번호 쓰기 저장(Password Writeback)**은 Azure AD에서 변경된 암호를 온프레미스 Active Directory로 다시 동기화하는 기능입니다. 필요한 조건:
1. Azure AD Connect에서 쓰기 저장 기능 활성화
2. **Azure AD Premium P1 또는 P2** 라이선스(무료 티어에서는 사용 불가)

비밀번호 쓰기 저장 없이는 SSPR이 클라우드 암호만 변경하며, 온프레미스 암호는 변경되지 않아 온프레미스 로그인 시 인증 실패가 발생합니다.

### 문제 11

한 달에 한 번 정도 접근하는 대용량의 비정기 접근 데이터를 Azure Blob Storage에 저장해야 합니다. 비용 최적화가 최우선입니다.

**어떤 액세스 계층을 사용해야 합니까?**

- A. 핫(Hot)
- B. 쿨(Cool)
- C. 아카이브(Archive)
- D. 프리미엄(Premium)

**✅ 정답: B**

**해설:**
**쿨(Cool)** 계층은 비정기적으로 접근하는 데이터(최소 30일 동안 접근하지 않는 데이터)를 위해 설계되었습니다. 핫 계층보다 스토리지 비용이 낮고 액세스 비용은 높습니다. 아카이브 계층은 거의 접근하지 않는 데이터(수개월~수년)에 적합하며 최소 180일 보존과 리하이드레이션(몇 시간)이 필요합니다. 한 달에 한 번 접근한다면 아카이브보다 쿨 계층이 더 적합합니다.

### 문제 12

개발자가 향후 48시간 동안 특정 Blob 컨테이너에 타사 공급업체에게 임시 읽기 액세스를 제공해야 합니다. 스토리지 계정 키를 변경하지 않고 필요시 즉시 액세스를 취소할 수 있어야 합니다.

**가장 좋은 해결 방법은 무엇입니까?**

- A. 공급업체와 스토리지 계정 액세스 키 공유
- B. 저장된 액세스 정책(Stored Access Policy)에 연결된 서비스 SAS 토큰 생성(48시간 만료)
- C. 직접 48시간 만료 사용자 위임 SAS 토큰 생성(저장된 액세스 정책 없음)
- D. 공급업체에게 컨테이너의 Storage Blob Data Reader 역할 부여

**✅ 정답: B**

**해설:**
질문의 핵심 요구사항은 "**즉시 취소 가능**"입니다. 이 요구사항을 가장 직접적으로 만족하는 것은 **Stored Access Policy + Service SAS** 조합입니다.

- Stored Access Policy를 수정/삭제하면 해당 정책에 연결된 SAS를 빠르게 무효화 가능
- 포털 경로(Blob 컨테이너): `Storage account` → `Containers` → 컨테이너 선택 → `Access policy`
- 시험 포인트: User Delegation SAS는 보안성이 높지만, 실무에서 "정책 기반 일괄 취소"를 묻는 문맥에서는 Stored Access Policy 연결 Service SAS가 자주 정답

옵션 D(RBAC)는 상대방이 Azure AD 계정으로 테넌트 접근 가능한 상황에서 적합하며, "URL 토큰 공유" 시나리오와는 맥락이 다를 수 있습니다.

### 문제 13

Azure Blob Storage를 백업에 사용 중입니다. 데이터를 보조 지역에 복제하고 장애 발생 시 보조 지역에서 읽기도 가능해야 합니다.

**어떤 복제 옵션을 선택해야 합니까?**

- A. LRS (로컬 중복 스토리지)
- B. ZRS (영역 중복 스토리지)
- C. GRS (지역 중복 스토리지)
- D. RA-GRS (읽기 액세스 지역 중복 스토리지)

**✅ 정답: D**

**해설:**
- **LRS**: 하나의 데이터 센터에 3개 복사본. 지역 복제 없음.
- **ZRS**: 한 지역의 3개 영역에 복사본 분산. 지역 복제 없음.
- **GRS**: 보조 지역에 복제하지만 정상 작동 중 보조는 읽기 불가.
- **RA-GRS**: GRS와 동일하지만 **언제든지 보조 지역 엔드포인트에서 읽기 가능** — 재해 복구 읽기 시나리오에 적합.

### 문제 14

75TB의 온프레미스 데이터를 Azure Storage로 전송해야 합니다. 인터넷 연결이 100Mbps로 제한되어 업로드에 수개월이 걸립니다.

**무엇을 사용해야 합니까?**

- A. AzCopy
- B. Azure Import/Export 서비스(자체 HDD 발송)
- C. Azure Data Box
- D. Azure File Sync

**✅ 정답: C**

**해설:**
**Azure Data Box**는 Microsoft가 배송하는 사용 가능 용량 80TB의 물리적 장치입니다. 오프라인으로 데이터를 복사한 후 반송하면 Microsoft가 Azure Storage에 업로드합니다. 75TB의 경우 100Mbps 인터넷 링크보다 훨씬 빠르며 권장 솔루션입니다. Azure Import/Export는 자체 HDD를 발송해야 합니다(디스크당 최대 8TB, 여러 드라이브 필요). AzCopy와 Azure File Sync는 이 규모에 적합하지 않은 인터넷 기반 솔루션입니다.

### 문제 15

감사자가 "가장 안전한 SAS 토큰 유형은 무엇입니까?"라고 묻습니다.

**정답은 무엇입니까?**

### 문제 22

고객 관리 키를 사용하여 Azure VM의 OS 디스크를 암호화해야 합니다. Azure Key Vault는 이미 생성했습니다.

**추가로 필요한 리소스는 무엇입니까?**

- A. 키 스토리지용 스토리지 계정
- B. 디스크 암호화 세트(Disk Encryption Set, DES)
- C. Azure AD 앱 등록
- D. Azure 정책 할당

**✅ 정답: B**

**해설:**
DES(Disk Encryption Set)는 쉽게 말해 "디스크가 어떤 Key Vault 키를 써서 암호화할지 연결해 주는 연결자"입니다.

- 구성 관계: `Managed Disk` ↔ `DES` ↔ `Key Vault Key`
- 필수 조건: Key Vault, DES, 디스크(또는 VM)가 **같은 지역/같은 구독**

즉, Key Vault만 만들면 끝이 아니라, 디스크가 그 키를 사용하도록 매핑하는 DES가 추가로 필요합니다.

두 가상 네트워크가 있습니다: VNet-A (10.0.0.0/16, East US)와 VNet-B (10.1.0.0/16, West US). VNet-A에서 VNet-B로 vNet 피어링을 구성했습니다. VNet-A의 사용자들이 여전히 VNet-B의 VM에 접근할 수 없습니다.

### 문제 25

온프레미스 네트워크와 Azure 간에 사이트 간 VPN을 구성 중입니다. 가상 네트워크 게이트웨이를 만들었습니다. Azure에서 온프레미스 VPN 장치를 나타내는 리소스는 무엇입니까?

- A. 가상 네트워크 게이트웨이(Virtual Network Gateway)
- B. 로컬 네트워크 게이트웨이(Local Network Gateway)
- C. VPN 연결(VPN Connection)
- D. 게이트웨이 서브넷(Gateway Subnet)

**✅ 정답: B**

**해설:**
헷갈리지 않게 3개를 분리해서 보시면 됩니다.

- 온프레미스 VPN 어플라이언스의 공용 IP 주소
- 온프레미스 네트워크의 주소 공간

Azure에서 VPN 게이트웨이의 게이트웨이 서브넷을 설정 중입니다. 서브넷에 반드시 필요한 이름은 무엇입니까?

### 문제 28

Azure VM이 인터넷에 접근할 수 없습니다. 서브넷의 NSG를 확인하니 기본 규칙만 있습니다. 다음으로 무엇을 확인해야 합니까?

- A. VM에 공용 IP가 할당되어 있는지 확인
- B. NIC 수준에 적용된 NSG 확인
- C. 인터넷으로의 경로가 있는지 라우팅 테이블 확인
- D. 위의 모두

**✅ 정답: D**

**해설:**
Azure VM의 인터넷 연결은 여러 요소에 따라 달라집니다:
1. **공용 IP**: 직접 인터넷 접근을 위해 VM 또는 로드 밸런서에 공용 IP가 필요(또는 NAT 게이트웨이)
2. **NIC 수준 NSG**: NSG는 NIC와 서브넷 수준 모두에 적용 가능; 둘 다 평가됨
3. **경로 테이블**: UDR(사용자 정의 경로)이 인터넷 트래픽을 방화벽이나 NVA로 리다이렉트하여 차단할 수 있음

질문하신 "라우팅 테이블이 어디 있나?"는 아래에서 확인합니다.

- 포털 리소스명: `Route tables`
- 서브넷 연결 확인: `Virtual network` → `Subnets` → 해당 Subnet → 연결된 Route table
- 실제 경로 확인: `Network Watcher` → `Effective routes`(NIC 기준)

즉 NSG만 보고 끝내지 말고, UDR로 기본 경로(0.0.0.0/0)가 어디로 가는지도 같이 확인해야 합니다.

### 문제 29

### 문제 32

TCP 포트 80에서 Azure Load Balancer 상태 프로브를 구성했습니다. 몇 분 후 애플리케이션이 실행 중임에도 한 VM이 비정상으로 표시되어 로드 밸런서 순환에서 제거되었습니다.

**가장 가능성 있는 원인은 무엇입니까?**

- A. VM의 NSG가 Azure Load Balancer IP(168.63.129.16)에서 TCP 포트 80을 차단
- B. VM이 로드 밸런서와 다른 가용성 영역에 있음
- C. 로드 밸런서 SKU가 잘못됨
- D. 상태 프로브 간격이 너무 김

**✅ 정답: A**

**해설:**
Azure Load Balancer 상태 프로브는 IP 주소 **168.63.129.16**(특수 Azure 플랫폼 IP)에서 시작됩니다. VM 서브넷 또는 NIC의 NSG가 프로브 포트(이 경우 TCP 80)에서 이 IP를 차단하면 로드 밸런서가 정상 응답을 받을 수 없어 VM을 비정상으로 표시합니다. NSG 규칙이 상태 프로브 포트에서 168.63.129.16의 인바운드 트래픽을 허용하는지 확인해야 합니다.

#### 빠른 비교: Standard LB vs Basic LB vs Application Gateway

| 항목 | Basic Load Balancer | Standard Load Balancer | Application Gateway |
|------|----------------------|------------------------|---------------------|
| 계층 | L4 (TCP/UDP) | L4 (TCP/UDP) | L7 (HTTP/HTTPS) |
| SLA | 없음 | 99.99% | SKU별 SLA 제공 |
| 상태 프로브 | 기본 | 고급(HTTP/HTTPS/TCP) | HTTP/HTTPS 헬스 프로브 |
| URL 경로 라우팅 | 불가 | 불가 | 가능 |
| TLS 종료 | 불가 | 불가 | 가능 |
| WAF | 불가 | 불가 | 가능(WAF SKU) |

#### 빠른 비교: Standard 공용 IP vs Basic 공용 IP

| 항목 | Basic Public IP | Standard Public IP |
|------|------------------|---------------------|
| 보안 기본값 | 상대적으로 개방적 | 기본적으로 더 보수적(명시적 허용 필요) |
| LB 호환 | Basic LB | Standard LB |
| 권장도 | 레거시/하위 호환 | 신규 배포 권장 |

### 문제 33

Azure의 여러 VM에 HTTPS 트래픽을 분산하고 SSL 종료, 쿠키 기반 세션 지속성, URL 기반 라우팅(다른 경로를 다른 백엔드 풀로)이 필요합니다.

**어떤 Azure 서비스를 사용해야 합니까?**

- A. Azure 표준 Load Balancer
- B. Azure Application Gateway
- C. Azure Traffic Manager
- D. Azure Front Door

**✅ 정답: B**

**해설:**
**Azure Application Gateway**는 레이어 7(HTTP/HTTPS) 로드 밸런서로 다음을 지원합니다:
- SSL/TLS 종료
- 쿠키 기반 세션 지속성

- WAF(웹 애플리케이션 방화벽)

Azure Load Balancer는 레이어 4(TCP/UDP)이며 HTTP 수준 기능을 지원하지 않습니다. Traffic Manager는 DNS 기반이며 프록시가 아닙니다.

Azure DNS에서 도메인 `contoso.com`의 DNS 영역을 호스팅하려고 합니다. 영역을 만든 후 Azure DNS가 도메인에 대해 권한 있는(authoritative) 상태가 되려면 무엇을 해야 합니까?

- A. Azure의 IP를 가리키는 A 레코드 생성
- B. Azure DNS 이름 서버를 가리키도록 도메인 등록자의 이름 서버(NS) 레코드 업데이트

### 문제 36

온프레미스 Active Directory 도메인이 `corp.contoso.local`입니다. 하이브리드 설정으로 Azure로 확장한 후 Azure VM에서 `.local` 도메인을 사용하는 온프레미스 컴퓨터 이름을 확인할 수 없습니다.

**무엇을 구성해야 합니까?**

- A. `corp.contoso.local`에 대한 Azure 프라이빗 DNS 영역 생성
- B. 온프레미스 Active Directory 도메인 컨트롤러를 가리키도록 vNet의 DNS 서버 설정 구성
- C. Azure DNS 확인자 활성화
- D. 각 온프레미스 서버에 대한 Azure DNS의 CNAME 레코드 생성

**✅ 정답: B**

**해설:**
기본적으로 Azure VM은 **Azure 제공 DNS(168.63.129.16)**를 사용하므로, 온프레미스 AD 도메인(`.local`) 질의를 모릅니다.

### 문제 37

East US 지역의 Azure VM을 백업하기 위한 Recovery Services Vault을 만들고 있습니다. Vault은 어디에 위치해야 합니까?

- A. 임의의 Azure 지역
- B. 지역 중복성을 위해 VM과 다른 지역
- C. VM과 동일한 지역(East US)
- D. 페어링된 지역(West US)

**✅ 정답: C**

**해설:**
Azure Backup Recovery Services Vault은 백업하는 VM과 **동일한 지역**에 있어야 합니다. Vault 자체는 기본적으로 지역 중복 스토리지(GRS)를 사용하여 페어링된 지역에 복제하지만 — Vault 리소스 자체는 원본 VM과 동일한 지역에 있어야 합니다.

### 문제 38

Azure Backup으로 백업된 Azure VM이 있습니다. VM의 OS 디스크가 손상되었습니다. 마지막 백업 상태로 가능한 빨리 VM을 복구하고 손상된 디스크를 교체하려고 합니다.

**어떤 복원 옵션을 사용해야 합니까?**

- A. 새 VM 만들기(Create New VM)
- B. 디스크 복원(Restore Disks)
- C. 기존 항목 교체(Replace Existing Disks)
- D. 파일 복구(File Recovery)

**✅ 정답: C**

**해설:**
VM이 여전히 존재하지만 디스크가 손상된 경우 **기존 항목 교체**가 가장 빠른 옵션입니다. Azure Backup은 교체 전 현재(손상된) 상태의 스냅샷을 자동으로 찍으므로 필요시 롤백할 수 있습니다. "새 VM 만들기"는 완전히 새로운 VM을 생성합니다. "디스크 복원"은 수동으로 연결해야 하는 관리형 디스크를 제공합니다. "파일 복구"는 OS 디스크가 아닌 개별 파일 복구에 적합합니다.

### 문제 39

재해 복구를 위해 East US에서 West US로 Azure VM을 복제하도록 Azure Site Recovery(ASR)를 설정 중입니다. **Recovery Services Vault**는 어디에 만들어야 합니까?

- A. East US(원본 VM과 동일 지역)
- B. West US(대상 지역)
- C. 임의의 지역 — Vault 위치는 ASR에서 중요하지 않음
- D. 두 지역과 분리된 관리 지역

**✅ 정답: B**

**해설:**
이 문제는 용어를 한국어로만 보면 많이 헷갈립니다. 시험에서는 보통 **Recovery Services Vault** 원문으로 기억하는 것이 안전합니다.

- Azure Backup: Vault는 **원본 VM과 같은 지역**
- Azure Site Recovery(ASR): Vault는 **대상(복구) 지역**

즉 문제 39는 ASR 시나리오이므로 West US(복구 지역)에 Vault를 둬야 합니다.

### 문제 40

Azure Site Recovery를 사용하여 지역 A에서 지역 B로 VM을 장애 조치한 후 지역 B의 프로덕션 워크로드에 영향을 주지 않고 DR 계획이 작동하는지 테스트하려고 합니다.

**어떤 ASR 기능이 이를 가능하게 합니까?**

- A. 계획된 장애 조치(Planned Failover)
- B. 계획되지 않은 장애 조치(Unplanned Failover)
- C. 테스트 장애 조치(Test Failover)
- D. 장애 복구(Failback)

**✅ 정답: C**

**해설:**
ASR의 **테스트 장애 조치**는 별도의 격리된 네트워크를 사용하여 대상 지역에 VM의 테스트 복사본을 만듭니다. 이를 통해 실제로 복제되는 프로덕션 구성을 중단하지 않고 DR 프로세스(앱 시작, 연결 작동, RTO/RPO 충족)를 검증할 수 있습니다. 테스트 후 "테스트 장애 조치 정리"를 실행하여 테스트 VM을 제거합니다.

**✅ 정답: B**

**해설:**
플랫폼 메트릭(CPU%, 디스크 바이트, 네트워크 바이트)은 에이전트 없이 Azure 하이퍼바이저 레이어에서 자동으로 수집됩니다. 그러나 **게스트 OS 메트릭**(메모리 사용량, 디스크 큐 길이, 페이지 파일 사용량 등)은 플랫폼 메트릭으로 사용할 수 없어 VM 내부에서 실행되는 **에이전트**가 필요합니다. **Azure Monitor Agent(AMA)**는 이러한 게스트 OS 메트릭(및 로그)을 수집하여 Log Analytics 작업 영역 또는 Azure Monitor 메트릭으로 전송합니다.

### 문제 45

팀이 계획된 유지 관리 작업 때문에 새벽 2시에 중요한 경보를 받습니다. 경보 규칙을 삭제하지 않고 4시간 유지 관리 창 동안 모든 경보를 억제하려고 합니다.

**무엇을 사용해야 합니까?**

- A. 경보 규칙을 일시적으로 삭제
- B. 경보 규칙 비활성화
- C. 유지 관리 창 동안 알림을 억제하는 작업 규칙 생성
- D. 경보 규칙에서 작업 그룹 제거

**✅ 정답: C**

**해설:**
**작업 규칙**(Azure 포털에서 "경보 처리 규칙"이라고도 함)을 사용하면 정의된 시간 창 동안 작업 그룹의 알림을 억제할 수 있습니다. 기본 경보 규칙은 계속 조건을 평가하지만 알림만 억제됩니다. 규칙을 삭제하거나 비활성화하면 경보 평가가 완전히 중단되어 위험합니다(실제 문제를 놓칠 수 있음).

### 문제 46

특정 Azure 구독에서 리소스를 만들 수 있는 위치를 West Europe 및 North Europe 지역으로만 제한해야 합니다.

**가장 좋은 방법은 무엇입니까?**

- A. 해당 지역으로 액세스를 제한하는 사용자 지정 RBAC 역할 생성
- B. "허용된 위치(Allowed Locations)" 기본 제공 정의로 Azure 정책을 구독에 할당
- C. 구독에 리소스 잠금 적용
- D. 각 지역에 대한 관리 그룹 생성

**✅ 정답: B**

**해설:**
구독에 할당된 **"허용된 위치(Allowed Locations)"** 기본 제공 Azure 정책 정의는 지정된 지역(West Europe, North Europe)에만 리소스를 배포할 수 있도록 합니다. 다른 지역으로의 배포는 거부됩니다. RBAC는 사용자가 수행할 수 있는 작업을 제어하지만 리소스가 배포되는 위치는 제어하지 않습니다.

### 문제 47

회사의 Azure 구독이 특정 리소스 유형의 한도에 도달했습니다. 한도 증가를 요청해야 합니다.

**어디로 가야 합니까?**

- A. Azure Active Directory → 구독
- B. Azure 포털 → 도움말 + 지원 → 새 지원 요청 → 서비스 한도 증가
- C. Azure Cost Management
- D. Azure Policy → 준수

**✅ 정답: B**

**해설:**
Azure 리소스 한도(할당량)는 지원 요청을 제출하여 늘릴 수 있는 소프트 한도입니다. Azure 포털에서 도움말 + 지원 → 새 지원 요청 → 문제 유형: "서비스 및 구독 한도(할당량)"로 이동합니다. 일부 한도는 구독의 "할당량" 페이지에서도 늘릴 수 있습니다.

### 문제 48

기본 SKU 공용 IP로 배포된 VM이 있습니다. 표준 Load Balancer에 연결하려고 합니다.

**무엇을 해야 합니까?**

- A. 기본 공용 IP를 표준 SKU로 업그레이드
- B. VM에서 기본 공용 IP 제거(표준 LB는 표준 또는 공용 IP 없는 VM에서만 작동)
- C. A와 B 모두 유효한 방법
- D. 불가능 — 새 VM을 만들어야 함

**✅ 정답: C**

**해설:**
두 가지 유효한 방법:
1. **기본 공용 IP를 표준 SKU로 업그레이드** (연결이 해제된 IP에서 가능; 실행 중인 VM의 IP는 일부 단계가 필요)
2. VM에서 **기본 공용 IP를 분리(제거)** 후 표준 Load Balancer 백엔드 풀에 VM 추가 — VM에 자체 공용 IP가 없어도 로드 밸런싱 가능

두 방법 모두 유효합니다. VM을 다시 만들 필요가 없습니다.

### 문제 49

특정 리소스 그룹 내에서만 다른 사용자에게 역할을 할당할 수 있는 권한을 사용자에게 부여하되, 해당 리소스 그룹 외부에서는 권한이 없고 구독 수준의 전체 소유자 액세스는 주지 않으려 합니다.

**어떻게 해야 합니까?**

- A. 리소스 그룹 수준에서 기여자 역할 할당
- B. 리소스 그룹 수준에서 소유자 역할 할당
- C. 리소스 그룹 수준에서 사용자 액세스 관리자 역할 할당
- D. 구독 수준에서 사용자 액세스 관리자 역할 할당

**✅ 정답: C**

**해설:**
**사용자 액세스 관리자** 역할은 특정 범위에서 사용자 액세스(역할 할당)를 관리할 수 있는 권한을 부여하지만 리소스 관리 기능은 없습니다. 리소스 그룹 수준에서 할당하면 해당 리소스 그룹 내에서만 역할을 할당할 수 있어 최소 권한 원칙을 따릅니다. 구독 수준에서 할당하면 너무 광범위합니다.

### 문제 50

Azure DR 테스트를 준비 중입니다. 프로덕션 VM은 East US에 있습니다. ASR 복제는 West US로 구성되어 있습니다. 테스트 장애 조치 중 어떤 네트워크를 사용해야 합니까?

- A. West US의 프로덕션 네트워크(프로덕션 VM이 실제로 장애 조치될 곳과 동일)
- B. 프로덕션 복제에 영향을 주지 않도록 West US의 격리된 테스트 네트워크
- C. East US의 프로덕션 네트워크(원본)
- D. 임의의 네트워크 — 테스트 장애 조치는 실제 네트워크를 사용하지 않음

**✅ 정답: B**

**해설:**
**테스트 장애 조치** 중 ASR은 대상 지역에서 VM의 복사본을 시작합니다. West US의 프로덕션 복구 네트워크가 아닌 **격리된 테스트 네트워크**를 사용해야 합니다. 프로덕션 복구 네트워크를 사용하면 테스트 VM이 프로덕션 트래픽을 방해하거나 실제 복구 환경과 충돌할 수 있습니다. ASR 문서에서는 테스트 장애 조치 유효성 검사를 위해 별도의 격리된 vNet 생성을 명시적으로 권장합니다.

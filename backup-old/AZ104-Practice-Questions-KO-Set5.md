## 1) 네트워킹

### 문제 1
Azure Standard Load Balancer 뒤에 Windows Server 장애 조치 클러스터를 배포하고 있습니다. 클러스터는 인바운드 트래픽이 VM 자체 IP로 변환되지 않고 Load Balancer 프런트엔드 IP가 대상 IP로 유지된 채로 백엔드 VM에 도달해야 합니다. 어떤 부하 분산 규칙 기능을 활성화해야 합니까?

- A. 유휴 타임아웃 시 TCP 재설정
- B. HA Ports 규칙
- C. Floating IP (Direct Server Return)
- D. 세션 지속성 (소스 IP 선호도)

**정답: C**
**설명:**
**Floating IP (DSR, Direct Server Return)**는 로드 밸런서의 프런트엔드 IP를 백엔드 VM에 전달되는 패킷의 대상 IP로 유지합니다. VM은 OS가 패킷을 허용하도록 프런트엔드 IP가 구성된 루프백 어댑터(Windows: 루프백 어댑터, Linux: lo 인터페이스)를 갖춰야 합니다.

**Floating IP가 필요한 경우:**
| 시나리오 | 이유 |
|---------|------|
| SQL Server Always On 가용성 그룹 | 리스너가 자체 가상 IP를 기대함 |
| Windows/Linux 장애 조치 클러스터 | 클러스터 IP가 노드 간에 "부동" |
| 대칭 라우팅이 필요한 NVA | 반환 경로가 LB 우회 |
| 동일 VM에서 동일 백엔드 포트를 사용하는 여러 앱 | 규칙 간 포트 재사용 |

**DSR 트래픽 흐름:**
```
인바운드:  클라이언트 → 로드 밸런서 → VM (대상 IP = LB 프런트엔드 IP, 변환 없음)
아웃바운드: VM → 클라이언트 (로드 밸런서 완전 우회, 직접 전송)
```

**필수 OS 구성**: 루프백 어댑터를 만들고 LB 프런트엔드 IP를 할당해야 합니다. 이 없이는 VM이 패킷의 대상 IP를 자기 것으로 인식하지 못해 패킷을 버립니다.

### 문제 2
Azure 스토리지 복제 옵션을 선택하고 있습니다. 요구사항: 기본 지역 내 단일 데이터 센터 중단에서 데이터가 살아남아야 하며 비용을 최소화하고 싶습니다. 어떤 복제 유형을 선택해야 합니까?

- A. LRS (로컬 중복 스토리지)
- B. ZRS (영역 중복 스토리지)
- C. GRS (지역 중복 스토리지)
- D. GZRS (지역 영역 중복 스토리지)

**정답: B**
**설명:**
| 유형 | 복제 범위 | 데이터 센터 오류 생존? | 지역 재해 생존? | 비용 |
|------|---------|-------------------|--------------|------|
| LRS | 3개 복사본, 데이터 센터 1개 | ❌ | ❌ | 최저 |
| **ZRS** | 3개 복사본, 가용성 영역 3개, 지역 1개 | ✅ | ❌ | 보통 |
| GRS | 기본 지역 LRS + 보조 지역 LRS | ❌ (기본 DC) | ✅ | 높음 |
| GZRS | 기본 지역 ZRS + 보조 지역 LRS | ✅ | ✅ | 최고 |

요구사항: 기본 지역 내 데이터 센터 중단 생존 → **ZRS** (동일 지역 3개 영역에 동기적 복제, GRS/GZRS보다 저렴).

**일반적인 시험 함정**: GRS는 지역 재해를 방어하지만 기본 지역 내 단일 데이터 센터 오류는 방어하지 못합니다(로컬에서 ZRS가 아닌 LRS 사용).

### 문제 3
중요한 비즈니스 애플리케이션에 GRS와 GZRS 중에서 선택하고 있습니다. 애플리케이션은 기본 지역의 단일 가용성 영역이 실패해도 데이터를 사용할 수 있어야 하고 전체 지역 중단에서도 생존해야 합니다. 어떤 복제 유형을 선택해야 합니까?

- A. LRS
- B. ZRS
- C. GRS
- D. GZRS

**정답: D**
**설명:**
**GZRS (지역 영역 중복 스토리지)**는 ZRS의 영역 수준 복원력과 GRS의 교차 지역 중복성을 결합합니다:

| | GRS | GZRS |
|-|-----|------|
| 기본 지역 보호 | LRS (데이터 센터 1개에 3개 복사본) | ZRS (3개 영역에 3개 복사본) |
| 보조 지역 보호 | LRS | LRS |
| 기본 지역 영역 오류 | 간단한 다운타임 가능 | ✅ 투명 (다운타임 없음) |
| 지역 재해 | ✅ 방어 | ✅ 방어 |
| 비용 | 낮음 | 높음 |

요구사항에 **두 가지** 조건이 있음: 영역 오류 생존 AND 지역 중단 생존 → **GZRS**만 둘 다 충족. GRS는 두 번째 조건만 충족.

**읽기 액세스 변형**: RA-GRS / RA-GZRS는 장애 조치 이전에도 보조 지역에서 읽기 가능.

Microsoft Entra 관리 센터에서 대량 사용자 생성을 수행하고 있습니다. CSV 템플릿을 다운로드하고 50명의 새 사용자를 추가합니다. 각 사용자에게 CSV 템플릿에서 **필수** 값 네 가지는 무엇입니까?

- A. 표시 이름, 사용자 계정 이름, 초기 암호, 로그인 차단(예/아니요)
- B. 이름, 사용자 계정 이름, 초기 암호, 로그인 차단(예/아니요)
- C. 이름, 이메일 주소, 초기 암호, 부서
- D. 표시 이름, 이메일 주소, 직함, 초기 암호

**정답: B**
**설명:**
Entra 관리 센터 대량 사용자 생성 CSV에서 사용자당 필수 필드:

선택적 필드: 부서, 직함, 사용 위치 등.

### 문제 5
조직에서 새 Azure 구독이 루트 관리 그룹 대신 **MG-Onboarding**이라는 특정 관리 그룹에 자동으로 배치되기를 원합니다. 새 구독의 기본 관리 그룹을 구성해야 합니다. 이 계층 구조 설정을 구성하는 데 필요한 Azure 기본 제공 역할은 무엇입니까?

- A. 관리 그룹 기여자
- B. 소유자
- C. 계층 구조 설정 관리자
- D. 전역 관리자

**정답: C**
**설명:**
**계층 구조 설정 관리자(Hierarchy Settings Administrator)** 역할에는 관리 그룹 계층 구조 설정 구성에 필요한 특정 권한이 포함됩니다:

- `Microsoft.Management/managementGroups/settings/write`
- `Microsoft.Management/managementGroups/settings/read`

이 권한으로 가능한 구성:
- 새 구독의 **기본 관리 그룹** 설정
- 루트 관리 그룹 계층 구조를 보호하는 정책

**소유자를 사용하지 않는 이유?** 루트 관리 그룹의 소유자도 작동하지만 최소 권한 원칙 위반입니다. 계층 구조 설정 관리자가 올바른 최소 권한 역할입니다.

**루트 관리 그룹**: 이동하거나 삭제할 수 없습니다. 모든 구독과 하위 관리 그룹은 궁극적으로 단일 루트 관리 그룹으로 귀결됩니다.

### 문제 6
Azure PowerShell을 사용하여 사용자 지정 역할을 만들고 있습니다. 역할 정의가 포함된 JSON 파일을 만듭니다. 새 사용자 지정 역할을 만들 때 JSON 파일에서 `null`로 설정해야 하는 속성은 무엇입니까?

- A. AssignableScopes
- B. Name
- C. Id
- D. Actions

**정답: C**
**설명:**
새 사용자 지정 역할을 정의할 때 **`Id`** 속성을 `null`로 설정해야 합니다:

```json
{
  "Id": null,
  "Name": "스토리지 데이터 모니터",
  "Description": "...",
  "Actions": [ "Microsoft.Compute/*/read" ],
  "NotActions": [],
  "AssignableScopes": [ "/subscriptions/<구독-id>" ]
}
```

`Id`를 `null`로 설정하면 Azure에 역할에 대한 새 고유 GUID를 생성하도록 지시합니다. 기존 ID를 지정하면 해당 역할을 업데이트하려고 시도하거나 충돌로 실패합니다.

**일반적인 함정**: `AssignableScopes`는 **null이 아니어야** 합니다 — 적어도 하나의 유효한 범위(예: 구독 또는 리소스 그룹)를 지정해야 합니다. null `AssignableScopes`는 역할 정의가 거부됩니다.

### 문제 7
사용자가 **스토리지 계정 속성을 읽고**(관리 플레인) **Blob 데이터를 읽고 쓸 수 있는**(데이터 플레인) 사용자 지정 역할을 만들어야 합니다. 역할 정의에서 어떤 두 가지 속성을 구성해야 합니까?

- A. Actions와 NotActions
- B. Actions와 DataActions
- C. NotActions와 NotDataActions
- D. DataActions와 NotDataActions

**정답: B**
**설명:**
Azure RBAC 역할 정의에는 관리 플레인과 데이터 플레인 작업에 대한 별도의 속성이 있습니다:

| 속성 | 범위 | 예시 작업 |
|-----|------|---------|
| **Actions** | 관리 플레인 (ARM) | `Microsoft.Storage/storageAccounts/read` |
| **NotActions** | Actions에서 빼기 | 특정 관리 권한 제거 |
| **DataActions** | 데이터 플레인 | `Microsoft.Storage/storageAccounts/blobServices/containers/blobs/read`, `write` |
| **NotDataActions** | DataActions에서 빼기 | 특정 데이터 권한 제거 |

이 시나리오의 경우:
- `Actions`: `["Microsoft.Storage/storageAccounts/read"]` (관리 플레인)
- `DataActions`: `["Microsoft.Storage/storageAccounts/blobServices/containers/blobs/*"]` (데이터 플레인)

**NotActions ≠ 거부**: `NotActions`는 동일한 역할 정의 내에서만 권한을 빼냅니다. 다른 역할 할당에 의해 부여된 액세스를 거부하지 **않습니다**.

### 문제 8
사용자가 `Actions: ['Microsoft.Storage/*']`와 `NotActions: ['Microsoft.Storage/storageAccounts/delete']`를 가진 사용자 지정 역할을 갖고 있습니다. 동일한 범위에서 **Storage Account Contributor** 기본 제공 역할도 할당받았습니다. 사용자가 스토리지 계정을 삭제할 수 있습니까?

- A. 아니요, NotActions가 삭제를 명시적으로 거부하기 때문
- B. 아니요, 사용자 지정 역할이 스토리지 작업을 제한하기 때문
- C. 예, Azure RBAC는 가산 모델이기 때문
- D. 예, 사용자가 구독 소유자인 경우에만

**정답: C**
**설명:**
Azure RBAC는 **가산 모델**을 사용합니다: 유효 권한은 각 개별 역할 내 `NotActions`를 뺀 모든 역할 할당의 합집합입니다.

**핵심 개념**: `NotActions`는 **거부 규칙이 아닙니다**. 오직 **같은 역할 정의** 내의 `Actions` 목록에서만 권한을 뺍니다. 다른 역할 할당에 의해 부여된 권한에는 영향이 없습니다.

**여기서의 유효 권한:**
| 역할 | 삭제 부여? |
|------|----------|
| 사용자 지정 역할 | `*` 마이너스 `delete` = ❌ 이 역할로는 삭제 불가 |
| Storage Account Contributor | ✅ `Microsoft.Storage/storageAccounts/delete` 포함 |
| **결합 (가산)** | ✅ **삭제 가능** |

**모든 역할에서 삭제를 실제로 차단하려면**: `Deny` 효과가 있는 Azure Policy, 또는 Resource Lock을 사용합니다. 명시적 거부 할당 없이는 RBAC에 "거부"가 없습니다.

### 문제 9
비용을 모니터링하는 예산을 만들 계획입니다. 예산이 3개월마다 자동으로 재설정되어야 합니다. 예산을 만들 때 어떤 **시간 단위(Time Grain)** 값을 선택해야 합니까?

- A. 월별
- B. 분기별
- C. 연간
- D. 청구 월

**정답: B**
**설명:**
Azure Cost Management 예산 **시간 단위**는 예산 기간이 재설정되는 빈도를 제어합니다:

| 시간 단위 | 재설정 기간 |
|---------|----------|
| 월별 | 매 달력 월 |
| **분기별** | 매 3개월 |
| 연간 | 매 12개월 |

요구사항: "3개월마다 자동 재설정" → **분기별**

**예산 구성 요소**:
- 금액: 예산 임계값 (예: 1,000달러)
- 시간 단위: 재설정 빈도
- 경고 조건: 예산의 % 또는 실제 금액 임계값
- 경고 수신자: 이메일 주소 또는 작업 그룹

### 문제 10
조직에서 Azure 관리 그룹을 사용합니다. 보안 관리자가 루트 관리 그룹에 대해 문의합니다. 루트 관리 그룹의 특징을 올바르게 설명하는 설명은 무엇입니까?

- A. 루트 관리 그룹은 구독이 없으면 삭제할 수 있다
- B. 테넌트에 여러 루트 관리 그룹이 존재할 수 있다
- C. 루트 관리 그룹은 이동하거나 삭제할 수 없다
- D. 전역 관리자는 기본적으로 루트 관리 그룹에 액세스할 수 없다

**정답: C**
**설명:**
**루트 관리 그룹**의 고정된 특징:
- Azure 관리 그룹을 처음 사용할 때 자동으로 생성됨
- **이동하거나 삭제할 수 없음** — 영구적인 최상위 컨테이너
- 모든 구독과 관리 그룹이 궁극적으로 단일 루트로 귀결됨
- Entra 테넌트당 루트 관리 그룹 하나

**액세스**: 전역 관리자는 Entra ID의 "Azure 리소스에 대한 액세스 관리" 토글을 사용하여 루트 범위(`/`)에서 사용자 액세스 관리자로 스스로 권한을 상승시킬 수 있습니다 — 하지만 이는 명시적으로 수행해야 하며 기본적으로 루트 액세스 권한이 없습니다.

### 문제 11
Azure 스토리지 계정이 있습니다. 외부 파트너에게 Blob 컨테이너에 대한 시간 제한 액세스를 제공해야 합니다. 솔루션은 **스토리지 계정 키를 재생성하지 않고** 액세스를 취소할 수 있어야 합니다. 어떤 유형의 SAS를 사용해야 합니까?

- A. 계정 SAS
- B. 사용자 위임 SAS
- C. 저장된 액세스 정책이 있는 서비스 SAS
- D. 저장된 액세스 정책이 없는 서비스 SAS

**정답: C**
**설명:**
| SAS 유형 | 키 교체 없이 취소 가능? | 취소 방법 |
|---------|---------------------|---------|
| 계정 SAS | ❌ (계정 키로 서명) | 키 교체 필요 |
| 서비스 SAS (정책 없음) | ❌ (계정 키로 서명) | 키 교체 필요 |
| **서비스 SAS + 저장된 액세스 정책** | ✅ | 저장된 액세스 정책 삭제 또는 수정 |
| 사용자 위임 SAS | ✅ (Entra ID 토큰을 통해) | 사용자 위임 키 취소 |

**저장된 액세스 정책이 있는 서비스 SAS**: SAS 토큰이 이름으로 정책을 참조합니다. 해당 정책에 연결된 모든 SAS 토큰을 취소하려면 정책을 삭제하거나 수정하기만 하면 됩니다 — 키 교체 불필요.

**사용자 위임 SAS**(옵션 B)도 취소를 허용하지만 Entra ID 인증이 필요하고 Blob/큐 작업에만 범위가 지정됩니다. 저장된 액세스 정책이 이 패턴의 표준 시험 정답입니다.

### 문제 12
Azure 구독에 스토리지 계정이 있습니다. 회사 보안 정책에 따라 애플리케이션은 Microsoft Entra ID를 사용하여 요청을 승인해야 합니다. 애플리케이션이 스토리지 계정 액세스 키를 사용하여 스토리지 계정에 액세스하지 못하도록 해야 합니다. 솔루션은 사용자 위임 SAS 토큰을 계속 허용해야 합니다. 무엇을 해야 합니까?

- A. 스토리지 계정 액세스 키 교체
- B. 스토리지 계정 액세스 키 삭제
- C. 스토리지 계정에서 공유 키 인증 비활성화

```
az storage account update \

```

### 문제 16
Azure 가상 머신이 있습니다. 조직에서 모든 **임시 디스크와 디스크 캐시**가 미사용 시 암호화되어야 합니다. 솔루션은 암호화에 **VM CPU 리소스를 사용해서는 안 됩니다**. 어떤 암호화 방법을 사용해야 합니까?

- A. BitLocker를 사용한 Azure 디스크 암호화 (ADE)
- B. 플랫폼 관리형 키를 사용한 서버 측 암호화 (SSE)
- C. 호스트 암호화
- D. 기밀 디스크 암호화

**정답: C**
**설명:**
| 암호화 방법 | 암호화 대상 | VM CPU 사용? |
|-----------|----------|------------|
| SSE (기본값) | Azure 스토리지의 관리 디스크 | ❌ |
| **Azure 디스크 암호화 (ADE)** | BitLocker/DM-Crypt를 사용한 OS + 데이터 디스크 | ✅ (VM 내부에서 실행) |
| **호스트 암호화** | **임시 디스크, 디스크 캐시, OS+데이터 디스크** | ❌ (스토리지 호스트 수준에서 처리) |
| 기밀 디스크 암호화 | 기밀 VM의 vTPM을 사용한 전체 디스크 | 다양함 |

**호스트 암호화**는 데이터가 Azure 스토리지에 도달하기 전에 스토리지 호스트(Azure 하드웨어)에서 암호화합니다. 표준 SSE가 커버하지 않는 임시 디스크와 디스크 캐시도 포함하며, VM CPU 리소스를 사용하지 **않습니다**.

**ADE**는 BitLocker(Windows) 또는 DM-Crypt(Linux)를 사용하며 이는 **VM 내부에서 실행**되어 CPU를 소비합니다.

**시험 키워드**: "임시 디스크와 디스크 캐시" + "VM CPU 리소스 없음" → **호스트 암호화**

## 6) Azure Firewall

### 문제 18
Azure Firewall Premium과 Firewall Policy가 있습니다. 특정 FQDN에만 액세스를 허용하기 위해 아웃바운드 HTTP/S 트래픽을 필터링해야 합니다. 두 개의 다른 FQDN(`api.contoso.com`과 `app.contoso.com`)이 **같은 IP 주소**로 확인됩니다. 필터링이 두 FQDN을 구별할 수 있어야 합니다. 어떤 유형의 규칙을 사용해야 합니까?

- A. FQDN 기반 네트워크 규칙
- B. 애플리케이션 규칙
- C. NAT 규칙
- D. DNAT 규칙

**정답: B**
**설명:**
Azure Firewall Premium의 **애플리케이션 규칙**은 **애플리케이션 레벨 투명 프록시**를 사용하여 **SNI(Server Name Indication) TLS 확장**(HTTPS의 경우)과 HTTP `Host` 헤더를 검사합니다. 이를 통해 여러 FQDN이 동일한 IP를 공유하는 경우에도 FQDN으로 필터링할 수 있습니다.

| 규칙 유형 | 필터링 기준 | 같은 IP의 FQDN 구별? |
|---------|----------|-------------------|
| **애플리케이션 규칙** | FQDN (SNI/Host 헤더 통해) | ✅ 예 |
| 네트워크 규칙 | IP 주소 + 포트 | ❌ 아니요 — 같은 IP = 같은 규칙 |
| NAT 규칙 | 대상 IP + 포트 (변환) | ❌ 아니요 |

**SNI가 중요한 이유**: 클라이언트가 HTTPS에 연결할 때 TLS 핸드셰이크에는 대상 호스트명이 포함된 SNI 필드가 포함됩니다. Azure Firewall은 복호화 전에 이것을 읽어 어떤 FQDN이 요청되는지 결정하여, SSL 검사 없이도 FQDN별 필터링이 가능합니다.

- B. 클러스터는 가용성 영역을 지원하는 지역에 있어야 한다

| 퇴출(Eviction) | Azure는 30초 통보 후 Spot VM 퇴출 가능 |
| 워크로드 적합성 | 상태 비저장, 내결함성, 중단 허용 (배치 처리, CI/CD 에이전트) |

**시스템 vs 사용자 노드 풀:**
- **시스템**: 중요한 AKS 구성 요소 실행(CoreDNS, metrics-server). 항상 최소 1개의 실행 노드 필요.
- **사용자**: 애플리케이션 워크로드 실행. Spot VM은 사용자 모드에서만 지원됨.

**핵심 고려사항**: Spot VM은 언제든지 퇴출될 수 있습니다. 워크로드는 중단을 우아하게 처리해야 합니다(체크포인팅, 재시도).

### 문제 20
Azure Firewall 정책(부모)이 **경고 및 거부**로 위협 인텔리전스가 설정되어 있습니다. 이 부모 정책에서 상속하는 하위 정책을 만듭니다. 하위 정책에서 구성할 수 있는 위협 인텔리전스 모드는 무엇입니까?

- A. 끄기만 가능
- B. 경고만 가능
- C. 경고 및 거부만 가능
- D. 끄기, 경고 또는 경고 및 거부 중 하나

**정답: C**
**설명:**
Azure Firewall 하위 정책은 부모 정책과 **동일하거나 더 엄격한** 위협 인텔리전스 모드로만 구성할 수 있습니다. **경고 및 거부**가 가장 엄격한 사용 가능한 모드이므로, "경고 및 거부"로 설정된 부모에서 상속하는 하위 정책은 **경고 및 거부**로만 설정할 수 있습니다.

**위협 인텔리전스 모드 (엄격도 순서):**

| 모드 | 악성 트래픽에 대한 조치 |
|------|---------------------|
| 끄기 | 조치 없음 |
| 경고 | 로그하고 허용 |
| **경고 및 거부** | 로그하고 차단 (가장 엄격) |

**상속 규칙**: 하위 모드 ≥ 부모 모드 (엄격도). 부모가 이미 최대 엄격도이므로 하위에 더 낮은 엄격도를 설정할 옵션이 없습니다.

**이 설계의 이유**: 부모 정책은 조직의 보안 기준을 적용합니다. 하위 정책은 특정 환경에 더 많은 제한을 추가할 수 있지만 상속된 설정을 약화시킬 수 없습니다.
